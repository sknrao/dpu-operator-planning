OPI NVIDIA parity plan

Working plan, 16 Nov 2026. Assumes dpu-operator PRs 7 (vendor provider) and 8 (Helm chart on a network function) are merged. Supersedes the earlier milestone split wherever the two disagree; the differences are listed at the end.

NVIDIA should present the same user path as Intel and Marvell: label a host, apply DpuOperatorConfig, attach pods with the existing OPI CNI, and apply a ServiceFunctionChain. DPF stays unmodified. The adapter turns each OPI request into a DPF object, and DPF's own controllers do the work on the BlueField. The user never writes a DPF object.

1. The three names

They are one product and two processes inside it. "Adapter translator" is a controller inside the manager, and it is a separate binary from the VSP.

Adapter

The whole companion, repo opi-nvidia-dpf-adapter. It owns no OPI API and no DPF API. It watches OPI objects and writes DPF objects, and it installs the pinned DPF operator.

Today it ships as one image with two long-running processes: the manager (one cluster Deployment) and the VSP (one pod per BlueField host). A third binary, opi-daemon, is a stand-in for the real daemon and goes away.

Deployed in opi-nvidia-dpf-adapter-system. PR 7 can deploy the manager from dpu-operator when vendor=nvidia.
Adapter VSP

The node process, cmd/vsp. It is the vendor plugin the dpu-daemon dials on /var/run/dpu-daemon/vendor-plugin/vendor-plugin.sock. Intel and Marvell have the same kind of plugin; theirs programs the card directly.

Today it discovers the BlueField and writes identity annotations on the DataProcessingUnit. In the target it also answers Init, GetDevices, SetNumVfs, CreateBridgePort, DeleteBridgePort, and the OPI heartbeat.

Runs on the host, one pod per node. Talks gRPC to the daemon and writes a few DPF objects.
Adapter translator

The controllers inside the manager, pkg/translation, driven by the FieldMapping YAML in config/mappings. One reconciler per mapping. It watches an OPI object and server-side-applies the DPF objects that mapping lists.

It does not speak gRPC and it does not run on the node. The lifecycle manager is its sibling in the same process: that one Helm-installs DPF and registers VendorProvider/nvidia. When this plan says "the translator", it means the mapping controllers.

Runs in the manager Deployment. Cluster scoped. Writes DPF provisioning objects, chains, and DPUService.

A request crosses them in this order. The daemon calls the VSP. The VSP either answers from the node (device list, heartbeat) or writes one DPUServiceInterface. The translator, watching OPI objects from the manager, keeps the DPF chains and the provisioning objects in line. DPF's own controllers then program the card and br-sfc.

2. Flow now and target flow

Flow now is how the lab actually runs today. The operator and the adapter were installed separately, and the operator's daemon is not on the BlueField host. The target is the revised lifecycle: the adapter is loaded first, and it owns everything that knows about DPF.

Flow now

Two separate installs. No OPI data path. DPF objects for traffic are applied by hand.

1

Person
Installs dpu-operator with the lab script into openshift-dpu-operator, and installs the adapter separately with make deploy.

2

Adapter manager
Starts translator and lifecycle manager. Registers VendorProvider/nvidia as Available. Lifecycle manager installs or adopts DPF. Because the provider is already Available, PR 7's "deploy the adapter" step does nothing.

3

Adapter VSP
DaemonSet runs on the NFD label hardware.opiproject.org/profile=nvidia-bluefield. It annotates identity. It does not serve BridgePort, and its heartbeat is on the wrong gRPC service for the real daemon.

4

dpu-operator
dpu-daemon DaemonSet stays at 0 pods. No node has the dpu=true label it selects on. Detection, the device plugin, and the CNI server never start on this host.

5

Person
Applies the DataProcessingUnit by hand. The VSP stamps serial, PCI address, and product name onto it.

6

Translator
Emits DPUDevice, DPUFlavor, BFB, and DPU for a BlueField-3.

7

DPF, unmodified
Flashes the card, joins the Kamaji tenant, creates the host VFs from NUM_OF_VFS. VF0 is the host-to-DPU management channel.

8

Translator
Sets DPFReady. Nothing sets the OPI Ready condition, because the daemon is absent. The opi-daemon shim can write it, which is why that shim has to go.

9

Person
Applies DPUServiceInterface and DPUServiceChain by hand (the lab VF/SF samples). DPF's sfc-controller programs br-sfc. Traffic works. The OPI CNI is not in this path.

Target flow

Same user steps as Intel and Marvell. The adapter is loaded before any card is detected.

1

User
Installs dpu-operator and applies DpuOperatorConfig with vendor=nvidia.

2

dpu-operator
Deploys the adapter manager (PR 7) when VendorProvider/nvidia is not yet Available. This happens before detection. An adapter already installed out of tree is left alone.

3

Adapter manager
Lifecycle manager installs or checks DPF. Registers VendorProvider/nvidia carrying the PCI IDs and product name the daemon should detect. Deploys the VSP DaemonSet, and an NFD rule that labels BlueField-3 hosts dpu=true.

4

dpu-daemon
Lands on the labelled host. Its provider-driven detector matches the published PCI IDs, de-duplicates the two ports by serial, and creates one host DataProcessingUnit, nvidia-bf-<serial>-host. The operator does not render a VSP pod for this product.

5

Translator
Creates the DPF provisioning objects, tracked by annotation with no owner reference. DPF flashes the card and creates the VFs. A later daemon restart recreates the same CR name and re-adopts the same DPF objects, so it cannot trigger a reflash.

6

Adapter VSP
Init stays Unavailable until the DPF DPU is Ready, then returns 127.0.0.1 and serves BridgePort plus the OPI lifecycle heartbeat. The daemon advertises the spare VF PCI addresses as openshift.io/dpu. Ready becomes True. SetNumVfs checks the count and never writes sysfs.

7

Pod attach
A pod on default-sriov-net makes the CNI call CreateBridgePort. The VSP applies a DPUServiceInterface of type vf for that VF, never VF0. The translator holds one default chain: the host-VF selector to uplink p0. DPF programs br-sfc.

8

ServiceFunctionChain
The operator's SFC reconciler skips a network function that has a Helm chart. The translator builds the per-node chain (host VFs to the first function, between functions, last function to p0), two service interfaces per function on the br-sfc NAD, and a DPUService for the chart.

9

Teardown
The translator deletes DPF objects only after the OPI object has been gone longer than a grace period. DpuOperatorConfig removal is the full teardown.

Why the daemon still has to run. The feature parity with Intel and Marvell is the default-sriov-net network, the openshift.io/dpu resource, and the CNI server. Those are served by dpu-daemon. The adapter cannot import that code, because it lives under internal/. So the daemon runs, and the adapter answers it.

4. Findings that shape the plan

  1. A daemon restart would reflash the DPU if the adapter kept owner references from the DataProcessingUnit. On shutdown the daemon deletes every DPU CR on its node, and garbage collection would then delete the DPF DPU and BFB. The adapter avoids this with annotation tracking, a delayed delete, and re-adoption by the deterministic CR name. That keeps the fix out of dpu-operator.
  2. The daemon overwrites the whole status. Every Ready change assigns currentDpuCR.Status = dpuCR.Status, which erases DPFReady and DPFHardwareCompatible. This is a two-line bug fix and it affects every vendor.
  3. The current VSP would break the real daemon. The device plugin requires GetDevices to return VF PCI addresses. The VSP returns the card serial. Its heartbeat is registered on the dpu-api package, while the daemon calls the OPI lifecycle HeartbeatService. No BridgePort service is registered, and SetNumVfs only echoes.
  4. DPF already creates the host VFs, and VF0 belongs to DPF. The lab shows 46 VFs on PF0, matching NUM_OF_VFS=46 in the DPUFlavor. No adapter script creates them. VF0 (pf0vf0 on br-comm-ch / br-dpu) is the management channel. A Marvell-style write of 0 then N to sriov_numvfs would cut the DPU off from its Kamaji cluster. Spike S1 confirms this before the code relies on it.
  5. PR 8 leaves the SFC reconciler creating a pod from nf.Image. A chart network function has an empty image, so the reconciler would create a broken pod that also consumes two openshift.io/dpu devices. One guard skips chart network functions.
  6. The daemon expects a peer at the address Init returns. For Intel and Marvell that peer is the daemon on the DPU. For NVIDIA the VSP is that peer, on localhost, so nothing OPI-related runs on the BlueField.

Chains, owned by the translator, one per DPU node

Node stateDPF DPUServiceChain
No service chain targets the nodeopi-default-<dpu>: one switch, ports [host-VF selector, uplink p0].
Service chain with functions n1 … nkSwitches [host VFs, n1-in], [n1-out, n2-in], …, [nk-out, p0].

Ports select interfaces by label, so the chain stays put while pods come and go. The VSP only adds and removes labelled interfaces. The translator also emits a physical DPUServiceInterface for p0.

The CNI does not replay CreateBridgePort after a VSP restart, so interfaces are owned by the host Node and tied to their deterministic name. On start, the VSP deletes an interface whose VF is back in the host network namespace, which means no pod holds it.

The earlier "do not delete DataProcessingUnit objects on daemon shutdown" change is dropped from dpu-operator. The adapter handles a recreated CR by name, so a daemon restart is safe without changing shutdown behaviour for Intel and Marvell.

7. Adapter work, in build order

A. Detection and the host CR

Depends on spikes S1, S2, and S6.

  • Publish the PCI IDs and product name on VendorProvider/nvidia so the daemon's generic detector can match a BlueField-3.
  • Keep deploying the VSP DaemonSet from the adapter. Add the NFD rule that sets dpu=true on BlueField-3 hosts, which is what lets the daemon land.
  • Init returns Unavailable until the DPF DPU for this serial is Ready, then serves on localhost. The daemon already retries Init forever, so the CR shows Ready=False while DPF provisions.
  • Register the OPI lifecycle HeartbeatService. Ping is healthy only while the DPF DPU and its Kamaji node are Ready.
  • Gate the provisioning mapping on product NVIDIA BlueField-3 and isDpuSide=false. Drop the declared-versus-observed double check, since the detector now sets the product name.
  • Track DPF provisioning objects by annotation. Delete them only after the OPI CR has been gone for a grace period, or when DpuOperatorConfig is removed. A recreated CR re-adopts by name.
  • Remove cmd/opi-daemon and ReportReady. ReportReady also wrote Ready on DpuOperatorConfig, which conflicts with the operator. Keep the annotator inside the VSP process: the daemon updates spec, so annotations survive.

B. VF attach and the default network

Depends on spikes S3 and S4. No further dpu-operator change: the daemon, CNI, and device plugin already make these calls.

  • GetDevices returns VF PCI addresses from VF1 up, never VF0.
  • SetNumVfs checks that DPF created enough VFs and returns that count. It never writes sriov_numvfs.
  • CreateBridgePort and DeleteBridgePort apply and delete the vf DPUServiceInterface.
  • The translator holds the default chain (host VFs to p0) and the p0 interface.
  • Interfaces are owned by the host Node. On restart the VSP drops an interface whose VF has returned to the host namespace.

C. Network functions and service chains

Depends on spike S5.

  • Two service interfaces per network function, on the br-sfc NAD. nvidia.com/bf_sf comes from the interface count. The SFC nodeSelector is mapped onto DPU nodes.
  • Per-node chain: host VFs to the first function, between functions, and the last function to p0.
  • Document the chart contract: a chart consumes the two interfaces DPF injects.
  • CreateNetworkFunction and DeleteNetworkFunction return Unimplemented.

Still outside this plan. Creating the DPUCluster and Kamaji, and choosing the BFB URL, are manual today. The lifecycle manager has to grow defaults for those before the flow above is fully hands-off. That is adapter work, and it is not required to prove the data path.

8. Spikes to run before coding

A spike is a short experiment that answers one question the design depends on, before the code assumes the answer. Each one has a fallback, so none of them blocks the plan. They are not a code change and not a test suite.

QuestionIf the answer is no
S1Who creates the host VFs, and which indexes does DPF reserve besides VF0?The pool start moves. SetNumVfs still must not write sysfs.
S2How does a host node map to its DPU node in the Kamaji tenant, and which labels can a nodeSelector use?The translator learns whatever label the dump shows. Objects still have to land on that node.
S3Can one chain port's matchLabels select several VF interfaces, and do those VFs then share L2?The translator lists one port per VF. The 50-port limit then caps the pool at 49.
S4How long does a vf DPUServiceInterface take to become Ready, and to appear on br-sfc?If it exceeds the CNI ADD timeout, CreateBridgePort returns once DPF has accepted the object.
S5What happens to live traffic when one chain replaces another, and can one interface sit in two chains at once?The translator drains one chain before installing the next, and reports the gap.
S6Do the VF operations the upstream CNI performs (MAC, VLAN, spoof check, trust) succeed on these mlx5 VFs, and is the CNI and device-plugin machinery present on this host?The host path needs a k3s-specific CNI install before M-style pod attach can work. Independent of DPF.

How to run it

Script: opi-nvidia-dpf-adapter/hack/lab-spike-nvidia-dataplane.sh, also make lab-spike-nvidia-dataplane. Run it on the lab host as root, with the DPU up. It is read-only unless ACTIVE=1.

cd opi-nvidia-dpf-adapter
bash ./hack/lab-spike-nvidia-dataplane.sh
ACTIVE=1 DPU_HOST=<bf-oob-ip> DPU_USER=ubuntu DPU_PASS=<pw> \
  bash ./hack/lab-spike-nvidia-dataplane.sh

ACTIVE=1 uses the two highest-numbered spare VFs (never VF0, never a VF already claimed, and it never writes sriov_numvfs). It moves them into throwaway network namespaces, applies spike-labelled DPUServiceInterface and DPUServiceChain objects, pings, swaps the chain, and removes everything on exit, including on failure or Ctrl-C. DPU_HOST is optional; without it the OVS ports, flows, and OVS timings are skipped. VF_A, VF_B, and SPIKE_NS override the choices.

Bring back /tmp/spike-nvidia-dataplane-<stamp>.tgz, or at least SUMMARY.txt. The archive contains serials and addresses, so it stays out of git. Output goes to /tmp for that reason.

9. Done when

  • After A. Applying DpuOperatorConfig with vendor=nvidia is enough. The host DataProcessingUnit appears on its own, DPF provisions the card, the real daemon reports Ready=True, and DPFReady stays set across a daemon restart. The card is not reprovisioned.
  • After B. A pod on default-sriov-net gets a VF, a DPUServiceInterface appears for it, and the default chain carries traffic to p0. Deleting the pod removes the interface.
  • After C. An SFC with a Helm chart produces the DPF service and the stitched chain. Pod to pod, pod to network function, pod to pod through a network function, and removal of the chain all work from OPI objects only. The empty-image pod no longer appears.

The upstream e2e suite (webhook, host workload pods, traffic between pods, SFC pod creation, pod to external, delete of the network function, more chains than resources) is the eventual bar. It is not a gate for this round.
